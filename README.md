# idle

The interface definition language compiler for [Rose](https://github.com/blancolioni/rose). It parses `.idl` files into an abstract syntax tree, and generates Ada packages from the tree for a target, using [Syn](https://github.com/blancolioni/syn).

The language is described in the IDL chapter of the Rose book (`doc/rose-book/idl.adoc` in the Rose repository).

## Status

idle replaces Rose's original IDL compiler (see #1), and Rose builds with it.

- **Interfaces:** the whole language: parents, procedures and functions with parameter modes and interface types, constants, and range, derived and enumeration types. The kernel target generates `Rose.Interfaces.<Name>`, with its endpoint ids, and its client and server packages.
- **Interfaces in groups** (#100, Rose ADR 0034). An interface or role can be named with its group, `interface Storage.Bank`, in the file `storage-bank.idl`, and every reference to it gives the group too: a parent, a parameter or result (`return interface Storage.Region`), or a role member, even from inside the same group. The interface is generated as `Rose.Interfaces.Storage.Bank`, with its `.Client` and `.Server`, and each of its group's interfaces also writes the group's package, `Rose.Interfaces.Storage`, which declares nothing. Generated names that are made from an interface's name use its last part, so the client type is still `Bank_Client`. Endpoint ids hash the full name, such as `rose.interfaces.storage.bank.reserve_storage(in word_64) return interface rose.interfaces.storage.region`. A name without a group is still accepted.
- **Records** (#113, Rose ADR 0013). `type File_Info is record Name : String; Size : Natural; end record;` declares a record in an interface, whose fields are scalars, strings and other records, declared earlier or by a parent. It becomes an Ada record type, with `Unbounded_String` for a string, and a codec, in the interface package's body: `Encoded_Length`, and `Encode` and `Decode` both into or from a buffer at `Last` and as functions of a whole `Storage_Array`. The encoding is fixed by the IDL: fields in order, a one-word scalar in 4 bytes and a two-word one in 8, little-endian, and a string as its length in 4 bytes then its bytes, padded with zeros to a multiple of 4. A record argument or result travels in the invocation buffer as its encoding, and its length comes back as a data word; it can be `in` or `out`, but not `in out`. A record that doesn't fit, or a buffer too short to decode, raises `Constraint_Error`, which is an error reply. Only the user and host targets have records; the kernel target refuses them.
- **Records that gain fields** (#114, Rose ADR 0048). A field can have a default, `Size : Bytes := 0;`: a number, an enumeration literal, `True` or `False`, or a string. Within a series a record only gains fields, at its end, each with a default, and has no versions. Each encoded record starts with a header word, its length in bytes in the low 24 bits and its number of fields in the high 8, so the two ends of an invocation can differ: a decoder reads the fields it knows, up to the sender's count, gives the rest their defaults, and skips fields it doesn't know. Each record has a type id, `File_Info_Type_Id`, the hash of `record rose.interfaces.shelf.file_info`, which `--list-endpoints` lists. `--list-fields` writes each record's fields with their types and defaults, one to a line, for Rose's check that records only gain defaulted fields.
- **Shared types** (#115). A type of another interface is named with that interface, such as `Size : Core.Units.Bytes` for the type `Bytes` of `Core.Units`, which is found as a parent is. It can be a parameter, a result, a record field or the parent of a derived type, on every target; the generated code names it in its own package, `Rose.Interfaces.Core.Units.Bytes`, and its endpoint form is qualified the same way, as a parent's type is. An interface with no subprograms, of its own or inherited, only declares types and constants: it gets its package but no client or server, and it can't be passed as `interface X`. Quantities such as `Bytes` and `Duration` are plain derived types, declared once in `Core.Units`; their unit symbols are part of text rendering (#118).
- **Endpoint ids** are derived from the source (#3). An `Endpoint_Id` aspect pins one.
- **User target** (#39, #40). The same packages, with the same names and encoding, for programs built with Rose's userland run-time system. An interface becomes an Ada interface type, `<Name>_Object`, in `Rose.Interfaces.<Name>`. The client type implements it, and raises `Rose.Interfaces.Objects.Invocation_Error` when a call fails. The server package declares `<Name>_Interface`, which a program implements and attaches an object of with `Attach` or `Publish`; one type can implement several. Each object type declares `<Name>_Cap`, the object's cap for the interface, which a client implements and a served object implements with its server package's `Cap_Of (Context, Object)`. An interface argument is an object of the interface, and an interface result is one too, built in place as a client (#44). A client gets its caps on its first call. A string result is a `String`, and an `out` or `in out` string a `Rose.Texts.Text` (#45). An interface that is a `Resource` (Rose ADR 0010) has clients whose `Close` calls `Release`, and on the user target a server that frees a released object's slot (#50), and a public `Detach (Context, Object)`, for a server that removes an object itself, such as one it keeps for a bank's holder when the bank is destroyed (Rose ADR 0014, rose#849). Its clients also have `Forget`, on both targets, which deletes the client's caps without releasing the object, for a client that has handed the object to someone else, who releases it (rose#403). A server package keeps no state of its own: the objects attached to a context are in the package's table in that context, an extension of `Rose.Server.Interface_Table`, whose handlers and `Owns` are given the context (registered with `Rose.Server.Register_Context_Handler`), so each context serves only its own objects (#108). The table's vector grows with the objects, so it has no limit on their number (#83), and maps find an object by identifier and by address. An attached object's identifier comes from `Rose.Server.New_Identifier`, unique in the process, and each handler is registered with its package's `Owns`, so the server packages of interfaces with a common ancestor can serve objects in one process; identifier 0 names a package's first object, as for a restore notice (#84). A command has the same units as for the kernel target (#43), but takes an interface argument as an object, and an `out` string as a `Rose.Command_Line.Text`. See "User-mode target" in the IDL chapter of the Rose book.
- **Commands, packages and roles** (#2, Rose ADR 0002). For a command, the kernel target generates the procedure spec the author implements, a main that receives the shell's launch invocation and calls it, and the command's metadata, in the `.rose_command` section of the executable. For an IDL package, it generates a package of its details. A role generates nothing; it is part of the commands that inherit it. Arguments can be `Boolean`, `Natural`, `Positive`, `String`, `String_List` or an interface.
- **Command clients** (#103). For a command, the user target also generates `<Command>_Client`, whose procedure `Call` makes the launch call on a command endpoint, which `Launch.Launch_Command` returns, as a program that launches the command makes it. Its parameters are the endpoint, then the command's role members and arguments in the order of the main's signature, and, for a replaceable server, `Previous` and `Saved`, which default to the null cap and are sent only if they are needed. Role members and interface arguments are caps, an `out` interface is an `out` cap, and an `out` string is a `Rose.Command_Line.Text`. The client is made of the calls of Rose's `Rose.Command_Line.Launch_Client`, the caller's half of `Rose.Command_Line.Launch`, and raises `Rose.Interfaces.Objects.Invocation_Error`, with the command's message, if the call or the command fails. `--command-client` generates only the clients of the commands it is given, and not their specs, mains or metadata, for a program that launches a command without its server. It needs `--target user`.
- **Host target** (#133, rose#1101). `--target host` builds a command for the host's own Ada run-time, to test it without booting Rose. An interface has only its package, the user target's, with its object type: a host process has no caps, so there is no client or server. A command's spec is the user target's, and its metadata has no linker section. Its main is built on Rose's `Rose.Command_Line.Host`: `Receive (Call, Metadata.Text)` binds the process's command line to the arguments by the metadata, as petal binds a command line; each interface argument and each role member that is an interface is an object of its interface's host backing, opened with `Open (Object, Interface_Argument (Call, N))`, the text the user gave or `""`; and `Fail` reports `Command_Failed`. `Receive` raises `Rose.Command_Line.Host.Stopped` once it has said why the command shouldn't run, and the main ends quietly. The standard streams need nothing, since they are the process's own. The backings come from the file `--host-backings` names, Rose's `interfaces/host-backings.txt`: a line per interface, `Interface_Name Package.Type`, with `#` comments. A server, a replaceable command, a system cap, an `out` argument, a list of interfaces and an interface with no backing are refused, and nothing is written for the command.
- **Modes, rights and transactions** (#55, Rose ADR 0012). A command argument is `in` or `out`, never `in out`: the mode is only the direction, and an `out` interface is a cap the command returns. What a command can do with an interface argument is its type. An `in` argument whose interface is `Transactional`, or inherits from it, is marked `transactional` (#78, Rose ADR 0026): the shell gives the command a version, which the command commits itself. Rose ADR 0026 removed the `Versioned` and `Live` aspects, which `transactional` replaces (#79), and idle reports either one as an error.
- **Transient commands** (#127, rose#524). A command with the `Transient` aspect has processes that are never saved in a checkpoint, so nothing they hold, such as a password, reaches the disk. The metadata marks it `transient`, and Rose's exec launches it as transient.
- **Failures** (#60). On the user target, an exception that an operation raises in a server, or that comes from reading its arguments, becomes an error reply, `Rose.Invocation.Exception_Raised`, and the client raises `Rose.Interfaces.Objects.Invocation_Error` for it, so the operation fails by raising in the caller. The reply carries no name or message for the exception. When the call fails, by raising or because it names no object, the server deletes the caps that came with it, which the kernel had already put in its table, so an operation that raises must not keep them (#95). The kernel target is for programs that can't propagate exceptions, so its servers have no handler.
- **Replaceable servers** (Rose ADR 0032, rose#865). `Replaceable => Pkg` on a server command means that a new version of the program can take over from a running one. The command needs the `Server` aspect and the `Cap_Set_Service` role, which the old version uses to make the cap set its `Caps` returns. Its metadata gains an `argument Previous` of `interface Replaceable`, the cap after the others, also given as `previous cap N`. A null cap means a fresh start. It also gains an `argument Saved` of `interface Reader`, the cap after `Previous`, also given as `saved cap N`: a saved state to restore from (Rose ADR 0032, section 10, rose#881). Neither is an argument of the command's procedure, and both names are reserved. Instead, the main calls `Rose.Replacement.Start (Previous, Saved, Restore_Caps, Pkg.Read_State'Access)` before the procedure, so the procedure starts from the old version's state, or the saved one. A saved state carries no caps, so `Restore_Caps` names each cap the command is given, by its argument's name, for `Read_State` to take instead. The main names its role members and `in` interface arguments in `Given`, and straight after `Receive` sets `Restore_Caps := Rose.Replacement.Arguments (Previous, Given)`, which gives each cap that the caller left null the old version's cap of the same name (#105, rose#901). It uses those caps everywhere, in `Use_Capabilities` and in opening its clients, so a caller can launch a new version with `Previous` alone. Stream roles aren't handed over. On the user target, `Attach` takes an optional `Identifier`, and `Identifier_Of` gives an attached object's identifier, so a new version can give each object the identifier it had, which clients' caps name.

## Usage

```sh
idle --target kernel -I interfaces -o generated timer.idl
idle --target user -o generated-user stream_writer.idl
idle --target host --host-backings host-backings.txt -I interfaces -o host touch.idl
idle --check interfaces/*.idl
```

- `--target TARGET` chooses the code generator: `kernel`, the default, for kernel-level code and servers built with Rose's kernel run-time system, `user`, for programs built with its userland run-time system, or `host`, for a command built for the host to test it (see above). A program uses one target, never two, since they generate packages with the same names.
- `--host-backings FILE` names the host backings, for `--target host`.
- `-o DIRECTORY` is where generated files are written (default: the current directory).
- `-I DIRECTORY` adds a directory in which to look for the declarations a file names, after the file's own directory.
- `--syntax-only` parses the files and reports errors, without generating anything.
- `--check` checks the files together, without generating anything: file names, endpoint ids that clash, and parents and types that are not found.
- `--list-endpoints` lists the endpoint ids of the interfaces, with the canonical forms they are derived from.

## Building and testing

idle depends on Syn, pinned to a checkout in `../syn`.

```sh
make          # build (alr build)
make test     # build, then run tests/run.sh
```

`tests/run.sh` parses a snapshot of Rose's interfaces (`tests/rose/`), compares generated packages, and the units generated for the commands in `tests/commands/`, with `tests/expected/`, the user target's packages and units for commands with `tests/expected-user/`, and the host target's with `tests/expected-host/`, using `tests/host-backings.txt`; checks the diagnostics for the files in `tests/errors/` and the other error directories, and compiles every expected Ada file with `-gnatyabcefhiklmnoprst -gnaty3 -gnatwe`.
